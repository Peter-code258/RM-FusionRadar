# RM-FusionRadar — RM 雷达系统研究性项目

基于主流开源方案的 RoboMaster 雷达系统研究性项目，以 **C++17** 为核心开发语言，将五大技术模块实现为可独立编译运行的 C++ 子系统，通过统一数据格式与 UDP 通信协议解耦，最终可集成到主系统。

> 设计理念：**模块化、解耦、可降级**。每个子系统独立成分支、独立编译、独立测试，通过统一 `Target` 结构与 UDP 协议插拔式接入融合中心。

```
                    ┌─────────────────────────────────────┐
                    │         多传感器融合处理中心           │
                    │  (feature/multi-sensor-fusion)       │
                    │  坐标转换 · 时间同步 · 数据关联 · 融合 │
                    └──────────────┬──────────────────────┘
                                   │ UDP 统一目标列表
           ┌───────────┬───────────┼───────────┬───────────┐
           ▼           ▼           ▼           ▼           ▼
   ┌────────────┐ ┌──────────┐ ┌─────────┐ ┌──────────┐ ┌──────────┐
   │ 激光雷达   │ │ SDR      │ │ 单目视觉 │ │ 无人机    │ │ 作战单位  │
   │ 点云感知   │ │ 无线电   │ │ 雷达     │ │ 跟踪反制 │ │ (输出)    │
   └────────────┘ └──────────┘ └─────────┘ └──────────┘ └──────────┘
```

采用**传感器级后融合架构**：各传感器独立感知、独立输出目标，融合中心仅在数据层进行时空对齐与状态融合。任一传感器失效时融合中心自动降级，不影响其它链路。

## 统一数据格式与通信协议

### 统一目标结构

所有子系统输出的目标均遵循 `rm_radar::Target`，确保融合中心只需对接一种数据格式：

```cpp
struct Target {
    uint32_t id;                 // 唯一目标 ID（融合后全局唯一）
    TargetType type;             // 目标类别：步兵/英雄/工程/哨兵/无人机/静态障碍
    Vec3 position;               // 世界坐标 (x, y, z) 米
    Vec3 velocity;               // 速度向量 (m/s)
    float confidence;            // 置信度 [0, 1]
    uint64_t timestamp_us;       // 硬件时间戳（微秒）
    uint32_t point_count;        // 点数（激光雷达）/ 包围盒像素数（视觉）
    float bbox[6];               // 3D 包围盒 [x_min,y_min,z_min,x_max,y_max,z_max]
};
```

### UDP 二进制协议

子系统间通过 UDP 传输二进制目标数据，**小端字节序**：

- **传感器 → 融合中心**：`[source:1B][count:uint32][Target × count]`
  - `source` 为 `SensorSource` 枚举值（0=LIDAR, 1=VISION, 2=SDR, 3=MONOCULAR）
- **融合中心 → 作战单位**：`[count:uint32][Target × count]`

默认端口分配：

| 方向 | 端口 |
|------|------|
| 激光雷达 → 融合中心 | 8800 |
| SDR → 融合中心 | 8801 |
| 单目视觉 → 融合中心 | 8802 |
| 无人机反制 → 融合中心 | 8803 |
| 融合中心 → 作战单位 | 8900 |

## 模块一：激光雷达点云感知

**分支**：`feature/lidar-pointcloud-perception` · **依赖**：PCL 1.12+, Eigen3

### 开发思路

激光雷达是赛场最可靠的 3D 感知源（不受光照影响、测距精度高），因此作为**主力感知**。核心思路是用经典点云处理流水线将原始点云转化为带 ID 的运动目标：

```
原始点云 → 直通滤波(ROI裁剪) → 体素下采样 → RANSAC地面分割
         → 八叉树欧式聚类 → 匈牙利匹配+卡尔曼跟踪 → 结构化目标
```

### 核心流水线与参数

| 步骤 | 算法 | 默认参数 | 说明 |
|------|------|----------|------|
| 直通滤波 | `pcl::PassThrough` | X[-8,8] Y[-15,15] Z[0.1,2.0] m | 裁剪 ROI，减少计算量 |
| 体素下采样 | `pcl::VoxelGrid` | 0.05 m（>15m 自动放宽到 0.08 m） | 平衡精度与速度 |
| 地面分割 | RANSAC 平面拟合 | 距离阈值 0.08 m，迭代 100 次 | 仅对 Z<0.5 m 区域拟合，提速 40% |
| 目标聚类 | 八叉树欧式聚类 | 半径 `0.35 + 0.012×distance` m | 动态半径适应远距离扩散 |
| 跟踪 | 匈牙利 + 常速卡尔曼 | 匹配阈值 0.5 m，丢失容忍 3 帧 | 输出稳定唯一 ID |

### 教学解说

1. **为什么先地面分割再聚类？** 赛场地面点占比可达 70% 以上，若不剔除，欧式聚类会把地面与车体粘连，导致无法分离目标。RANSAC 拟合地面平面后移除 inlier，剩余点即非地面目标。
2. **动态聚类半径的意义**：激光雷达角分辨率固定，同一辆车在 5m 处回波密集、在 20m 处点云稀疏。固定半径会导致远目标被拆成多个聚类。公式 `0.35 + 0.012×distance` 让半径随距离线性增长，匹配点云扩散规律。
3. **Z<0.5m 区域拟合优化**：地面点必然在较低高度，只对低空点做平面拟合可大幅减少 RANSAC 迭代样本数，实测提速约 40%。
4. **卡尔曼跟踪解决什么**：聚类只给出单帧位置，无法跨帧关联目标，也无法预测遮挡期间的轨迹。常速模型卡尔曼滤波维护 `[x,y,z,vx,vy,vz]` 状态，匈牙利匹配用欧氏距离代价完成帧间关联，丢失 3 帧内仍维持预测。

### 强制实现结点

- ✅ 动态聚类阈值：`0.35f + 0.012f * target_distance`
- ✅ 静态障碍物过滤：导入场地固定障碍物坐标模板，按位置匹配剔除
- ✅ 多雷达拼接接口：输入外参矩阵，双雷达点云统一到世界坐标系后再聚类

### 交付物

- 可独立编译的 CMake 工程，`lidar_perception` 可执行文件
- `LidarPerception` 核心类，标准 API：`initialize()` / `process(pointCloud)` / `getTargets()`
- `config/lidar_config.yaml` 全参数配置
- `test_lidar` 单元测试（6 项）

## 模块二：多传感器融合处理中心

**分支**：`feature/multi-sensor-fusion` · **依赖**：Eigen3, 原生 UDP Socket

### 开发思路

融合中心是系统的"大脑"，但**不做感知**，只做数据层的时空对齐与状态融合。采用**后融合（late fusion）**架构——各传感器独立输出目标级结果，融合中心接收后统一处理。这样每个传感器可独立升级、独立故障，不会拖垮整个系统。

```
多源目标(UDP) → 坐标转换(传感器→车体→世界) → 时间同步(插值/预测)
            → 匈牙利数据关联 → 动态加权融合 → 置信度管理 → 统一目标输出(UDP)
```

### 核心实现

| 环节 | 策略 | 关键参数 |
|------|------|----------|
| 坐标转换 | 三级变换链 `传感器→车体→世界` | 4×4 外参矩阵可配置 |
| 时间同步 | 硬件时间戳 + 线性插值；SDR 10Hz 用卡尔曼预测补到 30Hz | 插值容忍窗口 100ms |
| 数据关联 | 匈牙利匹配，欧氏距离为代价 | 匹配阈值 1.0 m |
| 状态融合 | 按目标距离动态加权（见下表） | SDR 权重 0.9 修正长期漂移 |
| 降级容错 | 三级降级：视觉失效→纯雷达+SDR；雷达失效→单目；全失效→SDR | 超时 500ms 判定故障 |

**动态融合权重**（按目标到雷达站距离）：

| 距离区间 | 视觉权重 | 雷达权重 | 说明 |
|----------|----------|----------|------|
| < 8 m | 0.7 | 0.3 | 近距离视觉分辨率高，占主导 |
| 8–15 m | 0.5 | 0.5 | 中距离均衡 |
| > 15 m | 0.2 | 0.8 | 远距离激光雷达更可靠 |

### 教学解说

1. **为什么用后融合而不是前融合？** 前融合（raw data fusion）需要统一各传感器的采样率与坐标系，工程复杂度高且耦合严重。后融合只交换目标级数据，接口清晰、故障隔离，更适合多传感器异构系统。
2. **时间同步的必要性**：激光雷达 10Hz、视觉 30Hz、SDR 10Hz，各传感器数据到达融合中心的时刻不同。若直接用最新数据融合，会引入时间偏差导致目标"拖影"。通过时间戳对齐到统一参考时刻，远距离目标用卡尔曼预测位置，可将融合延迟控制在 5ms 内。
3. **动态加权的依据**：视觉在近距离细节丰富但远距离像素少、定位误差大；激光雷达测距稳定但近距离点云过密。按距离切换权重是对两种传感器物理特性的工程折中。
4. **SDR 权重 0.9 的作用**：官方信息波坐标是"真值"，但更新慢（10Hz）。用高权重融合 SDR 可修正视觉/雷达的长期累积漂移，同时用其它传感器的高频数据补充中间时刻。

### 强制实现结点

- ✅ 目标置信度管理：每目标维护融合置信度，低于阈值自动移除，避免幽灵目标
- ✅ 统一数据格式：所有目标含 ID、世界坐标、速度、置信度、类别、时间戳
- ✅ 故障自动检测：传感器数据超时自动判定故障，无缝触发降级

### 交付物

- `FusionCenter` 核心类，支持多路 UDP 输入
- 统一目标列表 UDP 输出（端口 8900），可直接下发作战单位
- `config/fusion_config.yaml`（外参矩阵、融合权重、阈值）
- 调试终端：实时打印目标列表、融合状态、降级状态
- `test_fusion` 单元测试（6 项）

## 模块三：SDR 软件无线电感知

**分支**：`feature/sdr-radio-decoder` · **依赖**：C++17, CRC16, 原生 UDP（信号前端对接 GNU Radio）

### 开发思路

SDR 解码官方信息波是**唯一零误差的坐标来源**（官方裁判系统直接广播）。核心思路是在 C++ 层实现完整数据链路层解析：从 GNU Radio 输出的基带比特流中找到帧、校验、解包，再通过 UDP 发布给融合中心。

```
GNU Radio 基带比特流 → 帧同步(0xAA55) → CRC16 校验 → 协议解包
                  → 卡尔曼插值(10Hz→30Hz) → UDP 发布
```

### 核心实现

| 环节 | 策略 |
|------|------|
| 帧同步 | 搜索同步字 `0xAA55`，支持多重同步字校验，抗干扰定位帧起始 |
| 校验 | CRC-16，失败直接丢弃 |
| 解包 | 按官方协议解析：机器人 ID、x/y 坐标(float)、血量、弹量、状态字 |
| 信道扫描 | 赛前自动扫描 16 个信道，锁定信号最强的官方工作信道 |
| 插值 | 卡尔曼滤波将 10Hz 官方数据插值到 30Hz 平滑轨迹 |
| 发布 | UDP 向融合中心发布（端口 8801），与官方信息波同步 |

### 教学解说

1. **帧同步字的作用**：无线传输是比特流，没有"帧边界"。`0xAA55`（二进制 `10101010 01010101`）交替跳变，便于接收器在噪声中锁定帧起始位置。多重校验（要求连续出现 N 次）可降低误同步概率。
2. **为什么必须 CRC 校验**：无线信道有干扰，比特翻转会导致坐标完全错误。CRC-16 能检出绝大多数突发错误，校验失败直接丢弃比错误数据更安全——融合中心会用上一帧预测值代替。
3. **10Hz→30Hz 插值的意义**：官方信息波 10Hz，而作战单位决策周期是 30Hz。直接用 10Hz 数据会导致目标位置每 100ms 跳变一次。卡尔曼插值用常速模型预测中间时刻位置，输出平滑的 30Hz 轨迹，丢包时也能维持预测不跳变。
4. **字节序兼容**：不同硬件平台（x86 小端 vs 部分嵌入式大端）字节序不同，协议层提供大小端配置，避免跨平台解析错误。

### 强制实现结点

- ✅ 卡尔曼轨迹插值：10Hz 官方数据 → 30Hz 平滑输出
- ✅ 字节序兼容：支持大小端配置
- ✅ 丢包容错：连续丢包时维持轨迹预测，坐标不跳变

### 交付物

- `SdrDecoder` 协议解析核心库（输入比特流，输出结构化目标数据）
- UDP 数据发布节点
- `tools/channel_scan.cpp` 信道扫描与自动锁定工具
- 离线数据回放工具（支持录制数据回放调试）
- `test_sdr` 单元测试（7 项）

## 模块四：低成本单目视觉雷达

**分支**：`feature/mono-vision-radar` · **依赖**：OpenCV4, Eigen3

### 开发思路

在没有激光雷达的低成本方案下，用**单目相机 + 单应性矩阵（Homography）**实现全场定位。核心假设是：机器人在地面上运动，检测框底部中心点即地面接触点，通过标定好的单应性矩阵可将像素坐标直接映射到世界二维坐标。

```
相机输入 → 畸变校正 → 目标检测框(YOLO接入) → 地面接触点提取
        → 单应性矩阵映射 → 距离补偿 → 卡尔曼跟踪(含盲区预测) → 全局坐标输出
```

### 核心实现

| 环节 | 策略 |
|------|------|
| 畸变校正 | 导入相机内参矩阵与畸变系数，径向+切向畸变校正 |
| 场地标定 | 输入 ≥8 组「像素坐标-世界坐标」对应点，RANSAC 求解单应性矩阵 H |
| 目标映射 | 取检测框底部中心点为地面接触点，`P_world = H × P_pixel` |
| 盲区跟踪 | 导入场地障碍物几何模型，目标进入盲区时卡尔曼维持预测 |
| 重识别 | 目标离开盲区重新出现时，按位置+运动方向匹配原 ID，不发生 ID 切换 |

### 教学解说

1. **单应性矩阵的几何意义**：单应性矩阵 H 描述两个平面之间的投影映射关系。地面是一个平面，相机成像平面也是一个平面，因此地面点到像素点的映射可用 3×3 的 H 矩阵表示。标定 ≥8 组对应点用 RANSAC 求解 H，之后任意像素点乘 H 即得世界坐标。
2. **为什么取检测框底部中心**：机器人脚踩地面，检测框底部中心点最接近地面接触点，映射误差最小。若取框中心，高度差会导致远距离投影偏差。
3. **盲区跟踪的必要性**：赛场有掩体/障碍物，目标会短暂消失。若不处理，目标重出现会被分配新 ID（ID switch），导致决策混乱。卡尔曼滤波在盲区维持运动预测，重出现时用最近邻匹配找回原 ID。
4. **距离补偿与分区标定**：单应性映射假设目标高度为 0，但机器人有高度，远距离时检测框底部中心点投影会偏高。加入距离补偿系数修正，并支持场地分区标定（不同区域用不同 H），可将全场定位误差控制在 1.0m 以内。

### 强制实现结点

- ✅ 距离补偿：针对远距离高度差投影偏差，加入补偿系数
- ✅ 分区标定：支持场地分区标定，提升远距离精度
- ✅ 相机姿态校验：内置姿态偏差检测，相机晃动超阈值自动告警

### 交付物

- `MonoRadar` 完整模块，支持 USB 相机/视频流输入
- `tools/calibration_tool.cpp` 交互式标定工具：可视化点选标记点，自动计算 H
- 全参数配置：内参、单应矩阵、障碍物模型
- 实时可视化界面：画面 + 目标框 + 对应世界坐标
- `test_mono` 单元测试（6 项）

## 模块五：无人机跟踪与反制

**分支**：`feature/anti-drone-tracking` · **依赖**：OpenCV4, Eigen3, ESKF, 串口通信

### 开发思路

无人机目标小、速度快，单级跟踪难以兼顾"大范围搜索"与"高精度锁定"。采用**二级跟踪架构**：广角相机负责全局粗跟踪，将目标移入视野中心后切换长焦/振镜做亚像素精跟踪，最后用 ESKF 估计三维轨迹并控制激光反制。

```
广角相机(全局) → 粗跟踪检测 → 云台控制(目标居中)
        → 切换长焦/振镜(ROI) → 亚像素精定位 → ESKF 轨迹估计
        → 前馈伺服控制 → 激光反制(稳定度达标触发)
```

### 核心实现

| 环节 | 策略 |
|------|------|
| 粗跟踪 | 广角相机全局画面检测无人机像素坐标，控制云台转动使目标居中 |
| 精跟踪 | 切换小范围 ROI，亚像素级定位无人机中心 |
| 轨迹估计 | ESKF 误差状态卡尔曼滤波，估计三维运动轨迹并预测下一帧位置 |
| 伺服控制 | 输出云台/振镜控制量，对接下位机 1kHz 电流闭环 |
| 激光反制 | 跟踪稳定度达标后触发激光发射，持续照射计时与有效反制判定 |

### 教学解说

1. **为什么用二级跟踪**：广角相机视场大但分辨率低，长焦分辨率高但视场小。先用广角搜索目标并引导云台对准，再切长焦精跟踪，兼顾搜索范围与跟踪精度。振镜比云台响应快，用于末端精细修正。
2. **ESKF 与普通卡尔曼的区别**：普通卡尔曼直接估计状态（位置、速度），ESKF 估计"状态的误差量"。对于无人机这种姿态耦合的运动，ESKF 能将姿态误差与位置误差解耦估计，数值稳定性更好，适合高动态目标。
3. **前馈控制的作用**：伺服系统有跟随延迟（云台转动需要时间）。若只做位置闭环，目标快速移动时会滞后。加入目标速度前馈量（`控制量 = 位置误差×Kp + 目标速度×Kff`），可补偿延迟、提升跟踪带宽。
4. **光斑检测闭环**：激光光轴与相机视轴可能不同轴。通过检测激光打在目标上的光斑位置，闭环修正激光指向偏差，确保能量命中。

### 强制实现结点

- ✅ 前馈控制：加入目标运动前馈量，补偿伺服跟随延迟
- ✅ 光斑检测闭环：接入光斑检测数据，实时修正激光指向偏差
- ✅ 光轴标定：支持激光光轴与相机视轴的同轴度标定补偿

### 交付物

- `AntiDroneTracker` 跟踪与反制控制模块
- 云台/振镜控制串口协议库
- `ESKF` 误差状态卡尔曼滤波算法库
- 调试界面：跟踪框 + 预测位置 + 激光发射状态
- `test_anti_drone` 单元测试（8 项）

## 分支开发与集成流程

```
feature/* (独立开发 + 单元测试通过)
       │  git checkout -b feature/xxx (from main)
       │  开发 → cmake build → ./test_xxx
       ▼
   develop (多分支集成测试)
       │  验证跨子系统 Target 格式一致、UDP 互通、融合端到端
       ▼
   main (最终发布)
       └── 仅保留 common 公共库 + 集成说明文档
```

**分支命名规范**：`feature/<子系统英文名>`，如 `feature/lidar-pointcloud-perception`。

每个子系统分支均为独立的 CMake 工程，可单独编译运行与测试，互不干扰。

## 编译与部署教程

### 环境依赖

| 依赖 | 版本 | 安装（Ubuntu 20.04/22.04） |
|------|------|--------------------------|
| 编译器 | GCC 9+ / Clang 10+ | `sudo apt install build-essential` |
| CMake | 3.16+ | `sudo apt install cmake` |
| Eigen3 | 3.3+ | `sudo apt install libeigen3-dev` |
| nlohmann-json | 3.x | `sudo apt install nlohmann-json3-dev` |
| PCL（仅激光雷达分支） | 1.12+ | `sudo apt install libpcl-dev` |
| OpenCV4（仅视觉/反制分支） | 4.5+ | `sudo apt install libopencv-dev` |

### 编译单个子系统

以激光雷达为例：

```bash
git checkout feature/lidar-pointcloud-perception
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
make -j$(nproc)
```

### 运行

```bash
# 激光雷达感知（headless 模式，无 VTK 时自动降级）
./lidar_perception ../config/lidar_config.yaml

# 融合中心
./fusion_center ../config/fusion_config.yaml

# SDR 解码
./sdr_decoder ../config/sdr_config.yaml

# 单目视觉雷达
./mono_radar ../config/mono_config.yaml

# 无人机反制
./anti_drone_tracker ../config/anti_drone_config.yaml
```

### 运行单元测试

```bash
cd build
make -j$(nproc)
./test_lidar        # 激光雷达 6 项
./test_fusion       # 融合中心 6 项
./test_sdr          # SDR 解码 7 项
./test_mono         # 单目雷达 6 项
./test_anti_drone   # 无人机反制 8 项
```

### 系统部署（完整雷达站）

1. **硬件接线**：激光雷达接以太网、相机接 USB、SDR 接 USB、下位机接串口
2. **启动顺序**（依赖关系）：
   ```bash
   # 1. 先启动融合中心（数据汇聚点）
   ./fusion_center config/fusion_config.yaml &
   # 2. 启动各传感器子系统（向融合中心上报）
   ./lidar_perception config/lidar_config.yaml &
   ./sdr_decoder config/sdr_config.yaml &
   ./mono_radar config/mono_config.yaml &
   # 3. 融合中心通过 8900 端口向作战单位下发统一目标列表
   ```
3. **标定**：运行 `calibration_tool` 完成相机内参标定与单应性矩阵标定
4. **验证**：观察融合中心调试终端输出，确认各传感器目标正常融合

### 跨平台部署

- **x86 开发机**：直接按上述步骤编译
- **ARM 嵌入式（如 RK3588/Jetson）**：交叉编译或本机编译，PCL/OpenCV 需对应 ARM 版本
- 所有子系统纯 C++17 实现，无 ROS 强依赖，可移植性强

## 设计目标与技术选型

| 目标 | 实现方式 |
|------|----------|
| **模块化、解耦、可降级** | 后融合架构，传感器级独立，故障隔离，三级降级容错 |
| **兼容多档硬件** | 从入门级单目（OpenCV）到高端激光雷达（PCL）+ SDR |
| **赛场鲁棒性** | 卡尔曼跟踪、盲区预测、CRC 校验、置信度管理 |
| **统一接口** | 标准化 `Target` 结构 + UDP 二进制协议，子系统可插拔 |
| **实时性** | 激光雷达单帧 <10ms，融合端到端 <5ms，SDR 解析 <20ms |
| **可维护** | CMake 模块化、全参数 YAML 配置、分级日志、单元测试覆盖 |

### 技术选型理由

- **C++17**：性能关键路径需要零开销抽象，`std::optional`/`std::variant`/结构化绑定提升代码可读性
- **PCL**：点云处理事实标准，滤波/分割/聚类算法成熟稳定
- **OpenCV4**：计算机视觉基础库，单应性求解、畸变校正、图像处理一应俱全
- **Eigen3**：线性代数 header-only 库，矩阵运算高效，适合嵌入式交叉编译
- **原生 UDP**：避免 ROS 等重型框架依赖，轻量、低延迟、易部署到嵌入式平台
